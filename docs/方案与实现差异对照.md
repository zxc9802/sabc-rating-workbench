# SABC 方案文档与当前实现差异对照

对照对象：

- 方案文档：`/Users/a123/Downloads/SABC项目评价智能体完整方案.md`
- 当前实现：仓库 `SABC判断智能体（新）`，规则版本 `SABC-2.0.2`（`sabc/rating.py`）
- 产品自述：`PRODUCT.md` 写明实现依据是《SABC项目评级智能体_V2.0_产品与技术方案.docx》，不是上述完整方案

结论先说：

> 两边共用同一套骨架——程序算分、模型不改规则、未知不当 0 分、证据封顶、否决需核验证据、报告可追溯。  
> 但评的对象、八个维度、等级阈值、项目档案、财务模块、验证任务、报告结构和对话规则都不一样。  
> 当前产品是「公司内部立项评级工作台」，方案文档是「创业/个人项目决策辅助系统」。

## 1. 项目定位（文档第 1 节）

方案要求智能体回答四类问题：

1. 这个项目现在值不值得做？
2. 在什么条件下可以做？
3. 最可能失败的地方是什么？
4. 下一步应该先验证什么、怎么验证、什么时候停止？

最终判断应围绕：**项目机会 × 用户资源 × 当前阶段 × 可承受风险**。

当前实现实际回答的是：

1. 这个项目是否适合当前公司战略、预算、现金安全线和团队？
2. 证据够不够给正式等级？
3. 反方意见和关键假设是什么？
4. 前两条假设怎么验证（只有 method / pass / fail）？

缺了文档的「当前阶段」和「最大可承受风险」两个核心变量。首页文案「这个项目，现在值得做吗？」接近文档，但内部规则是公司立项逻辑。

| 阶段 | 方案要求 | 当前实现 |
|---|---|---|

## 3. 用户输入与项目档案（文档第 3 节）

### 3.1 项目基本信息

| 方案字段 | 当前实现 |
|---|---|
| 项目解决什么问题 | 无独立字段，可能写在 `description` |
| 为哪类客户服务 | `target_user` |
| 产品或服务是什么 | 无独立字段 |
| 客户目前如何解决这个问题 | **无** |
| 收费方式和预计价格 | 无独立字段，可能写在 `value_mechanism` |
| 主要竞争或替代方案 | **无** |

当前 7 个结构化项目字段：目标用户、经营目标、价值机制、成功指标、周期、首期投入、主要风险。另有名称、类型、原始描述。

### 3.2 用户目标

方案要求：副业还是长期创业、现金流还是规模、验证商业模式还是技术、期望回报和时间周期。

当前实现：**全部没有**。只有 `business_goal` / `success_metric` / `timeframe`，且是公司经营结果口径。

### 3.3 用户资源

| 方案字段 | 当前实现 |
|---|---|
| 可投入资金 | 公司 `budget` + 项目 `budget_requested` |
| 最大可承受损失 | **无**。公司有自由文本 `risk_policy`，规则引擎不读 |
| 每周可投入时间 | 无独立字段；公司 `team` 是自由文本 |
| 团队能力 | 公司 `team` / `capabilities` |
| 已有客户、渠道、技术、供应链 | **无结构化字段** |

文档强调：**可投入资金 ≠ 最大可承受损失，必须分开记录。**  
当前实现没有「最大可承受损失」。投入超过可用资源只把等级封顶到 B，不否决。

### 3.4 当前项目阶段

方案要求 7 档：只有想法 / 已做访谈 / 已有原型 / 已有试点 / 已有付费客户 / 已有稳定收入 / 准备扩张。

当前实现：**完全没有 `project_stage`。** 这是文档四个核心变量之一。

### 3.5 已有证据

方案列举：访谈、反馈、订单、合同、报价、成本、转化、复购、技术测试、供应商资料。

当前实现有证据对象（来源、期间、范围、核验状态、等级 E0–E3），但不按上述类型分类，也没有「用户陈述」这一类。

## 5–6. SABC 等级定义（文档第 5–6 节）

### 等级含义

两边都有 S / A / B / C，信息不足单独标记。含义大体接近，行动措辞不同：

| 等级 | 方案行动 | 当前实现行动 |
|---|---|---|
| S | 按里程碑扩大投入 | 集中资源，分阶段放大 |
| A | 启动受控试点 | 正式立项，分阶段投入 |
| B | 只做低成本验证 | 小规模验证，禁止重仓 |
| C | 暂停、调整或放弃 | 当前不立项 |
| U / NR | 补信息后再评价 | 补齐信息后再评级 |

### 分数阈值（硬差异）

代码：`base_score>=90 → S；>=75 → A；>=60 → B；否则 C`。

| 等级 | 方案 | 当前实现 |
|---|---|---|
| S | ≥85 | ≥90 |
| A | ≥70 | ≥75 |
| B | 55～69 | 60～74 |
| C | <55 | <60 |
| 信息不足 | U | NR |

同一套维度分，在两套规则下可能给出不同等级。例如总分 72：文档是 A，代码是 B；总分 58：文档是 B，代码是 C。

文档还要求最终等级不能只看总分，必须结合否决、封顶、证据强度、人工复核。  
当前实现结合了否决、`policy_caps` 封顶、证据等级封顶、S 级准入门；**没有「建议人工复核」输出**。

## 7. 八维评分体系（文档第 7 节）——核心差异

总分公式两边一致：

```text
总分 = Σ（维度权重 × 维度得分 / 5）
```

且都要求总分由程序计算，不允许模型心算等级。  
权重数字碰巧都是 20 / 15 / 15 / 15 / 10 / 10 / 10 / 5，但分给了不同维度。

| 权重 | 方案维度 | 当前实现维度 | 是否同一件事 |
|---|---|---|---|
| 20% | 客户需求与付费意愿 | 经营回报确定性 | 否 |
| 15% | 可触达市场与获客路径 | 战略匹配度 | 否 |
| 15% | 单位经济与盈利机制 | 市场空间 / 需求价值 | 否 |
| 15% | 创始人与团队匹配 | 资源匹配 / 凭什么赢 | 部分（公司资源 ≠ 创始人） |
| 10% | 差异化与竞争替代 | 可复制性与复利资产 | 否 |
| 10% | 资金与现金流承受力 | 现金流与资金效率 | 近似 |
| 10% | 技术与交付可行性 | 风险可控性 | 否（权重也对不上） |
| 5% | 关键依赖与风险可控性 | 机会成本 | 否 |

方案有、实现没有：付费意愿、获客路径、单位经济、创始人匹配、差异化、技术与交付。  
实现有、方案没有：战略匹配度、可复制性与复利资产、机会成本。

代码里搜不到「付费意愿 / 获客路径 / 创始人 / 差异化」作为评分维度。

## 8. 评分锚点（文档第 8 节）

方案要求每个维度建立明确的 0～5 分标准。例如「客户需求与付费意愿」：

| 分 | 方案锚点 |
|---:|---|
| 0 | 有可信证据证明目标客户基本没有该需求 |
| 1 | 问题存在，但优先级很低 |
| 2 | 问题明确，但付费主体和购买意愿不清楚 |
| 3 | 有明确目标客户和采购意向 |
| 4 | 已经产生真实付费和满意交付 |
| 5 | 已出现可重复付费、续费或复购 |

原则：未知必须记 `unknown/null`，不能当成 0 分。

当前实现：

- 未知不当 0、低分必须有已知负面事实——**这条对齐**
- 只有一句通用提示：5 显著优势，4 较强，3 基本成立，0～2 仅用于已知负面事实
- **没有任何维度的分档锚点表**
- 步长 0.5（方案未要求半档）

## 9. 硬性规则（文档第 9 节）

### 9.1 否决规则

| 方案示例 | 当前实现 |
|---|---|
| 当前方案明确违法 | 由模型写入 `vetoes`，需 `confirmed=true` 且证据已核验才判 C |
| 关键资源无法取得 | 同上，不是固定规则 |
| 必需投入超过用户最大损失承受能力 | **无此字段，也无此否决**。超可用资源只封顶 B |
| 商业模式存在明确不可持续结构 | 由模型判断，不是固定规则 |

### 9.2 等级封顶

| 方案示例 | 当前实现 |
|---|---|
| 尚无真实客户验证 | 模型可写入 `policy_caps`（B 封顶），不是程序硬编码 |
| 关键成本只是猜测 | 同上 |
| 获客渠道完全未经测试 | **无对应规则**（也没有获客维度） |
| 关键交付能力尚未验证 | 无对应规则 |

当前实现另有一套**确定性**封顶，方案没有写这么细：

- 证据 E0 / E1 → 最高 B
- 证据 E2 → 最高 A
- 证据 E3 → 才允许 S
- S 还要求战略/市场/回报/资源/复制五维 ≥4，且 `repeatable` / `resources_available` / `portfolio_feasible` / `review_complete` 全为 true
- 外部市场资料最多按 E1
- 过期或冲突证据降级

### 9.3 人工复核

方案建议在以下场景人工介入：法律适用不清、重大不可逆投入、证据互相冲突、超出已验证行业、高风险财务或合同。

当前实现：有人工评审表，用户可改八维和建议后让规则重算。  
**没有「本单建议人工复核」的规则输出**，证据冲突只是降级 + 警告。

## 10. 证据系统（文档第 10 节）

方案要求每条重要判断记录：

`claim_id / claim / claim_type / source_id / source_location / published_at / effective_at / retrieved_at / scope / verification_status`

`claim_type`：已核验事实 / **用户陈述** / 推算 / 假设 / 建议。

示例：用户说「已有 5 家客户愿意购买」只能先记为**用户陈述**，不能自动当成 5 家真实付费客户。

当前实现：

- 有证据对象：来源、期间、范围、核验状态、等级、是否重复验证、是否冲突、有效期
- 维度判断只有 `basis = fact / assumption / unknown`
- **没有 claim 层，没有 claim_type，没有「用户陈述」**
- 提示词允许「basis=fact 必须能说明用户事实或证据依据」——用户口述可被标成事实
- 实测 S01-1：8 个维度全部显示「事实判断」，证据等级 E0，0 条关联证据

## 11. 知识库建设（文档第 11 节）

方案建议五类知识资产：

| 知识库 | 方案内容 | 当前实现 |
|---|---|---|
| 评分规则库 | 维度、权重、锚点、等级、否决、人工复核 | 规则写死在 `rating.py` + 提示词，**无锚点库** |
| 行业资料库 | 模式、成本、渠道、KPI、失败原因、术语；须标地区/时间/行业/阶段/来源 | **无** |
| 案例库 | 成功 / 失败 / 中止 / 转型；区分当时已知与后来结果 | 有回测脚本，**无案例库** |
| 风险与合规库 | 法规、许可、限制、平台规则；优先官方来源 | 有法规/地方数据接口，**不是合规知识库** |
| 项目验证方法库 | 访谈、报价测试、付费试点、人工 MVP、Landing Page、预售、原型、渠道测试 | **无**；验证方法由模型临场编写 |

工程量实际投在文档未要求的地方开放数据（山东、福建、阿克苏、宿迁、黑龙江等地）。

## 12. 实时信息与知识库分工（文档第 12 节）

方案：知识库存稳定标准；实时检索查法规、市场、竞品、价格、平台规则、新技术。  
检索失败时必须说明：「本次未成功核验最新数据，因此结论只基于现有资料。」

当前实现：

- 有选源模型 + 外部取数（worldbank / github / sec / law / local / trends / web 等）
- 每轮最多 2 条查询
- 检索失败被静默处理（commit `d3fde89`）：对用户改写成「本轮依据已有资料继续分析」，并指示模型「不描述接口错误或取数故障」
- 手动取数失败只返回 `{status: skipped}`

**与文档要求相反。**

## 13. 财务分析模块（文档第 13 节）

方案要求计算必须由程序执行，模型只负责解释。至少支持：

| 模块 | 方案公式 / 内容 | 当前实现 |
|---|---|---|
| 单位经济 | 单位贡献额 = 单位净收入 − 单位变动成本 | **无** |
| 盈亏平衡 | 盈亏平衡销量 = 固定成本 / 单位贡献额 | 仅在重资产模板提示词里口头询问，**不算** |
| 现金流 | 何时收钱、何时支出、最低现金余额、是否资金断裂 | 只有可用资源上限 |
| 情景分析 | 悲观 / 基准 / 乐观；测售价下降、获客成本上升、回款延迟、交付成本上涨、客户流失 | **无** |

当前唯一确定性财务公式：

```text
可用上限 = min(新项目预算, 可用现金 − 现金安全线)，最低为 0
```

没有计算工具，提示词也未禁止模型心算。实测 A01-1 第 4 轮：80 万 − 50 万被说成「差 20 万」（应为 30 万），已记为质量关键错误。

## 14. 建议输出机制（文档第 14 节）

方案禁止「加强营销 / 做好产品 / 控制成本」这类空建议。每条重要建议应转为验证任务：

| 字段 | 方案 | 当前 `validation_plan` |
|---|---|---|
| 关键假设 | 有 | `claim` |
| 验证对象 | 找哪类用户 | **无** |
| 验证行动 | 具体做什么 | `method` |
| 预算 | 最多投入多少 | **无** |
| 时间 | 多久完成 | **无** |
| 成功指标 | 什么结果才算通过 | `pass` |
| 停止条件 | 什么情况下终止 | `fail` |
| 证据 | 需要提交什么数据 | **无** |

当前只输出排序后的前 **2** 条假设。原则「优先验证最可能改变最终结论的假设」部分对齐。

## 15. 强制比较多个方案（文档第 15 节）

方案要求每次重要决策比较：

1. 不做  
2. 延后

## 16–17. 系统架构与模块职责（文档第 16–17 节）

方案推荐：LLM 分析 + 知识检索 + 确定性计算 + 规则引擎 + 审核模块。流程为：

用户输入 → 项目结构化 → 完整度检查 → 追问 → 行业/阶段识别 → 知识库检索 → 实时核验 → 商业分析 → 财务计算 → 评分建议 → 规则引擎最终等级 → 风险/证据/逻辑审核 → 报告 → 验证任务 → 用户上传结果 → 重新评级。

| 方案模块 | 当前实现 |
|---|---|
| 信息提取 | 有。模型写 `project_patch`，用户到「项目资料」核对保存 |
| 追问 | 有，但每轮最多 2 问 |
| 检索 | 有选源 + 外部取数；失败静默 |
| 主分析模型 | 有，提八维建议，不出最终等级 |
| 财务工具 | **无** |
| 规则引擎 | 有 `assess()`，确定性算分、封顶、否决 |
| 审核模型 | **无独立审核模型**；人工评审表代替 |
| 报告模块 | 有，结构与文档第 21 节不完全对应 |
| 项目数据库 | SQLite，保存项目、公司版本、证据、评估快照 |

## 18. 技术实现（文档第 18 节）

方案 V1 建议：Dify + 大模型 API + 知识库 + 计算节点 + HTTP + PostgreSQL/Supabase。第一版先验证业务逻辑，不要先做复杂界面。

当前实现已是产品化 Web：Next.js 前端 + FastAPI + SQLite + 登录。  
文档把登录、项目管理、专家审核后台、数据看板、企业版、批量评价放在 V2。  
当前已有工作台、项目管理、报告历史，没有支付、权限体系（仅登录）、专家审核后台、看板、批量评价。

## 19. 数据结构（文档第 19 节）

方案每次评价至少保存：

`project_id / project_version / evaluation_id / evaluation_time / industry / region / project_stage / currency / status / grade / score / evidence_strength / dimension_scores / hard_gate_results / claims_and_sources / assumptions / financial_results / validation_tasks / review_results / model_version / rubric_version / calculator_version / source_snapshot_version`

当前快照有：项目、公司、证据、评分建议、规则版本、等级、业务分、证据等级、触发规则、验证计划。

缺失字段：`industry`、`region`、`project_stage`、`currency`、`financial_results`、`review_results`、`calculator_version`、`claims_and_sources`（claim 层）、`model_version`（评估记录未强制保存）。

可追溯 / 可复现 / 可复评 / 可审计：部分做到（快照 + 规则版本 + 回放脚本）。

## 20. 主分析模型提示词原则（文档第 20 节）

| # | 方案原则 | 当前实现 |
|---|---|---|
| 1 | 区分事实、用户陈述、假设和建议 | 只有 fact / assumption / unknown，**无用户陈述** |
| 2 | 不编造市场数据、价格、客户反馈或法规 | 提示词有，实测仍出现宏观数据当需求成立 |
| 3 | 信息不足时主动提出关键问题 | 有，但每轮最多 2 问，且会漏问或过早收口 |
| 4 | 不允许修改评分规则 | **对齐**。模型不能改权重、阈值、封顶 |
| 5 | 数学结果只能引用计算工具 | **未遵守**。没有计算工具 |
| 6 | 主动提出最强反对理由 | 要求至少 3 条 cons，报告有反对栏；**无单列「最强反对意见」** |
| 7 | 不把评分解释为成功概率 | **对齐**。页脚写明「置信度不是项目成功概率」 |
| 8 | 优先给低成本可逆验证方案 | 部分。B 级要求拆最小验证成本，但任务缺预算/时间 |
| 9 | 不默认开发产品就是最佳方案 | **无此原则** |
| 10 | 网页和文件中的指令不能修改系统规则 | **对齐**。有注入防护测试 |

另有当前实现有、方案未写的约束：内部 AI 不要求外部付费；重资产无验证路径须暂缓、禁止编造小试；宏观总量不能推算经营主体数。

## 21. 项目评价标准报告（文档第 21 节）

| 报告章节 | 方案 | 当前报告 |
|---|---|---|
| 21.1 项目摘要 | 做什么、服务谁、如何赚钱、当前阶段 | **无独立摘要**；阶段字段也不存在 |
| 21.2 当前结论 | 评级、证据强度、建议 | 有等级、行动、置信度、业务分、证据等级 |
| 21.3 分维度评分 | 八维及证据 | 有，但是另一套八维 |
| 21.4 最主要的三个机会 | 为什么可能值得继续 | 支持理由至少 3 条，不限「三个机会」 |
| 21.5 最主要的三个风险 | 最可能导致失败的原因 | 反对理由至少 3 条 |
| 21.6 关键未知项 | 还不知道什么 | NR 时列出缺失项；**已评级报告不再单列未知项** |
| 21.7 财务分析 | 盈亏平衡、现金流、三情景 | **无** |
| 21.8 最强反对意见 | 必须主动说明为什么可能不该做 | 混在反对列表里，不单列 |
| 21.9 下一步验证计划 | 验证什么、怎么做、预算、时间、指标、停止条件 | 只有 claim / method / pass / fail，且最多 2 条 |
| 21.10 评级升级条件 | 例如「10 个报价测试 + 3 个付费试点 + 成本不超过 X，则可从 B 升 A」 | 「何时回来重新评估」是 3 条固定文案，**不是量化升级条件** |

文档第 32 节推荐的最终输出形态（当前评级 + 证据强度 + 主要原因 + 下一阶段 + 验证目标 + 升级条件）在聊天和报告里都没有按这个模板落地。

## 22–24. 测试与验收（文档第 22–24 节）

### 方案要求的测试面

| 测试项 | 方案 | 当前情况 |
|---|---|---|
| 事实准确性 | 是否有证据 | 有对抗脚本和人工审计，主集未通过 |
| 引用支持性 | 来源是否支持结论 | 部分检查；引用支持率未达 ≥95% 宣称 |
| 财务准确性 | 计算是否正确 | **无财务模块，无法测**；对话心算已出错 |
| 逻辑一致性 | 分数与结论是否一致 | 规则单测覆盖封顶/否决/NR |
| 信息不足处理 | 是否正确返回 U | 返回 NR；门槛比文档更严 |
| 风险识别 | 是否识别重大风险 | 有规则测试；真实案例仍有漏问 |
| 抗诱导 | 用户要求高分时是否坚持规则 | 规则层已测；真实模型施压场景未全部通过 |
| 稳定性 | 换表达评级是否稳定 | 固定结构化输入稳定；自然语言仍有分差 |
| 建议可执行性 | 行动、预算、指标、停止条件 | 缺预算和时间 |

### 方案测试集规模

- 30～50 个真实案例修订规则
- 至少 200 个独立测试案例验收
- 覆盖：正常 / 明显好 / 明显差 / 边界 / 缺失 / 矛盾 / 高风险 / 诱导 / 注入 / 财务异常 / 过期资料

当前：规则单测约 78 项；质量验收主集规划 60 例 + 留出 8 例。`artifacts/goal-v4` 显示主集大多未完成，G01 增长类多记为失败，质量通过尚未宣称。

### 方案 V1 验收门槛 vs 现状

| 指标 | 方案目标 | 当前 |
|---|---:|---|
| 关键事实可追溯 | 100% | 未宣称达到 |
| 重大财务计算测试 | 100% 通过 | **无此模块** |
| 明确重大风险识别 | 100% | 未宣称达到 |
| 引用支持率 | ≥95% | 未宣称达到 |
| 信息不足正确处理 | ≥95% | 规则层有，真实访谈有过早收口 |
| 相同信息不同表达评级一致 | ≥95% | 自然语言稳定性未过关 |
| 与专家核心判断一致 | ≥85% | 无真实专家集 |

## 27–29. 实施路线、团队、第一版不要做什么（文档第 27–29 节）

方案 8 周：方法论 → 原型 → 测试 → 小范围试用（AI 评价 + 人工复核）。  
第一版不要：大量行业、十几个智能体、成功率预测、自动投资付款、大规模微调、复杂 App、过多炫酷功能。

当前实现：已经是完整 Web 工作台 + 登录 + 多数据源 + 选源模型，接近文档说的 V2 形态；评分方法论却不是这份方案。  
没有做成功率预测、自动付款、大规模微调——这几条对齐。  
「大量行业 / 复杂界面」这两条，当前实现比文档 V1 建议走得更远。

## 30. V1 产品闭环（文档第 30 节）

方案闭环：

```text
用户输入项目想法
  → 智能体追问
  → 形成项目档案
  → 查证关键事实
  → SABC 评价
  → 风险分析
  → 财务分析
  → 输出验证方案
  → 用户执行验证
  → 提交真实结果
  → 重新评级
```

当前闭环：

```text
填公司基线并确认
  → 新建项目（选四类模板）
  → 访谈追问（每轮最多 2 问）
  → 模型写入 pending_patch（侧栏进度仍可能是 0/7）
  → 用户必须到「项目资料」核对保存
  → 可选外部取数（失败静默）
  → 模型出评分建议
  → 用户到「评级报告」勾选确认
  → 规则引擎出 S/A/B/C/NR
  → 可再评估，旧报告保留
```

缺：财务分析、按方案结构的验证方案、用户提交验证结果后自动复评的闭环、项目阶段。  
多了：公司基线版本、人工评审表、地方数据源。

## 31. 产品核心竞争力（文档第 31 节）

方案认为长期壁垒是：评分体系、高质量案例、证据库、验证方法库、真实项目结果、复评数据、专家经验、持续改进的评价模型。

当前实际投入：确定性规则引擎、证据对象、外部数据源、访谈提示词。  
案例库、验证方法库、真实结果回流、专家经验：**未建立**。

## 32. 最终设计原则（文档第 32 节）

方案最重要的不是回答「这个项目能不能成功」，而是：

> 基于目前证据，这个项目值不值得进入下一阶段；如果值得，应该先验证什么；如果验证失败，什么时候应该停止。

推荐输出形态：当前评级、证据强度、结论、主要原因、下一阶段、验证目标、升级条件。

当前产品文案接近这句话，规则和报告却是「是否正式立项 / 是否禁止重仓 / 公司资源是否够」。  
没有「值不值得进入下一阶段」的阶段模型，也没有量化升级条件。

## 33. 对话与交互差异（方案未单列，实测暴露）

以下来自 `artifacts/goal-v4` 真实网页访谈，不是推断。

1. **每轮只问 2 个问题**，收敛慢，和方案 3～5 问不一致。
2. **评级门槛过严**：8 维全有分、≥3 条正反意见、≥1 条假设、7 个项目字段全知、公司 5 项全知且已确认、首期投入已知——任一缺失即 NR。方案的 U 是「关键信息不足」，不是「任何一项缺失」。
3. **侧栏进度与对话脱节**：模型抽到的事实先放 `pending_patch`，「N / 7 项已整理」只数已保存字段。S01-1 答了 4 轮仍显示 0/7。未保存时评估接口直接 422。
4. **检索失败对用户隐瞒**，与方案第 12 节相反。
5. **模型在对话里心算且算错**（80 万 − 50 万 = 20 万）。
6. **追问质量问题**（多条仍 open）：
   - 正文和 questions 重复，一轮出现 4 个问句
   - 用户说「未决定」后，下一轮换措辞再问同一件事
   - 未问收费方式就收口
   - 机会成本缺失但不主动追问
   - 新增事实后，某维分数从 3 回退为空
7. **评分依据问题**：
   - 痛点、付费意愿未知，仅凭宏观零售额把市场需求判 3 分 / fact
   - 把「目前未确认违规」「若未来发现合规问题」写成否决项
8. **技术错误直接给用户**：弹「评分建议格式无效，请检查维度、关键假设和确认条件」；另有连接超时。用户无法据此操作。
9. **无模型时是固定字段引导**，不是动态访谈。方案假设的是智能追问。

## 34. 做对了的部分（与方案一致）

- 总分由程序计算，模型只提建议，不输出最终等级
- 未知记 `null`，缺资料不直接判 C
- 低业务分必须有已知负面事实，不能因缺证据扣分
- 证据强度与业务分分开；E0/E1 不能升 A/S
- 否决需已确认 + 已核验证据
- 重复转载不增加证据等级；过期证据降级
- 提示注入防护：用户资料和文件中的指令不能改规则
- 每次评级保存公司 / 项目 / 证据 / 建议快照，带规则版本，可导出、可回放
- 明确「置信度不是项目成功概率」
- 不自动付款、签约、采购
- API Key 不进前端
- 有反方意见和关键假设，而不是只给一个分数

## 36. 若要对齐，有两条路

**方向 A：按完整方案重写规则层。**  
改 `rating.py`（维度、权重、阈值、锚点、否决、封顶、人工复核标志）、`llm.py`（提示词、每轮 3～5 问、字段集）、项目档案（阶段、最大可承受损失、用户目标、行业地区）、新增财务计算、按第 21 节改报告、验证任务 8 字段、多方案比较。现有约 78 项规则测试大部分要重写。

**方向 B：承认当前是另一套「公司立项」产品，回头改方案文档。**  
工作量小，但要放弃文档里的创业视角（付费 / 获客 / 单位经济 / 创始人 / 阶段）。

无论选哪条，对话层这几项都应单独修：模型心算、检索失败静默、侧栏与 `pending_patch` 脱节、技术错误文案、每轮问题数。
